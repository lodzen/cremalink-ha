cremalink_ha.select module

Select platform for the Cremalink integration.

Three selects per contracts/ha-entities.md:

  • Profile picker — occupied 0xA4 slots; selection sends a session-gated 0xA9; state is the last acked slot only.

  • Auto-off + water hardness — session-gated 0x90 writes with 0x95 read-back; state is always a machine-confirmed option.

class cremalink_ha.select.CremalinkBeanSelect(*args: Any, **kwargs: Any)[source]

Bases: _BaseSelect, RestoreEntity

BeanAdapt bean-system picker — options carry the user-assigned bean names from the d25X blobs (Device.bean_systems).

Selecting sends the real selection frame 0xB9 (device.select_bean_system) — a session-gated write on §13’s untested list, so the entity is gated on readiness like the profile select. current_option always reflects the machine’s flagged bean, never a locally remembered choice. The options+selection are persisted: standby blocks d25X re-reads, so a restart would otherwise leave the select empty until wake (FR-035 pattern).

class cremalink_ha.select.CremalinkProfileSelect(*args: Any, **kwargs: Any)[source]

Bases: _BaseSelect, RestoreEntity

Occupied profile slots; selection is a session-gated 0xA9 write.

Non-striker machines have no current-profile read-back — the app itself stores the selection app-side and only ever tells the machine (0x03EE is the striker register; it does not track 0xA9 selects on Soul). Device.refresh_current_profile therefore returns the last-asserted profile; the remembered selection is also restored after a restart. Like the official app, profile selection is the one setting that is unavailable in standby.

class cremalink_ha.select.CremalinkRecipeSelect(*args: Any, **kwargs: Any)[source]

Bases: _BaseSelect, RestoreEntity

Brewable-recipe picker — the single brew surface (spec FR-001..003).

Options are the machine-catalogued beverages (beverage_catalog — no duplicates, no one-shots). Selecting a recipe is local-only: it clears the recipe session’s overrides and re-arms the param load; no machine write happens here. The load itself runs in the background on coordinator updates via session.async_ensure_params. The entity is still gated on readiness like the profile select — changing the selection while the machine sleeps would discard the loaded overrides for a brew it cannot confirm anyway.

The recipe list itself is static (model table + command map — zero machine requests), so options exist immediately, even in standby or before the first monitor lands. Only the drink-menu order needs the machine (one GET per profile, cached) and is therefore fetched only while the machine is known to be awake (protocol.md §13/§14.12, research.md R11).
